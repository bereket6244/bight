# Blindfold training

How the blindfold drills work, and how to add to them without adding noise.

The engine game is a separate concern: see `ENGINE_INTEGRATION.md`.

## What this is for

Bight's other modes train *board sight* — where a square is, what a piece
attacks. Blindfold training trains something different: holding a position in
your head and **updating** it as moves go by. Those are separate skills, which
is why blindfold results are kept out of the square-mastery model entirely.

The progression the drills are built around:

```
coordinates → piece vision → tracking a short sequence
  → answering about the position it produced
  → rebuilding that position
  → losing the board a stage at a time
  → a whole game against an engine
```

## The three drills, and why only three

| Mode id | Card | Trains |
| --- | --- | --- |
| `blindfold-tracking` | Track a Position | Following moves and answering one targeted question |
| `blindfold-reconstruction` | Reconstruct a Position | Rebuilding what the moves produced |
| `blindfold-progressive` | Progressive Blindfold | The same, with visual help removed in stages |

Plus `blindfold-engine-game` (Blindfold vs Computer) when the engine ships.

**Variants live in setup pages, not in the mode browser.** The second pass
established that a mode list is a menu of *exercises*, not of settings, and the
guards in `secondPass.test.ts` enforce it: at most four cards per category, at
most four variants per mode. This is why the progressive ladder's six stages
are a setup control rather than six variants — stages differ only by how often
the board is redrawn, which is a setting.

## The question model

Every blindfold question is an ordinary `Question` with one extra block:

```ts
interface BlindfoldPresentation {
  startFen: string;        // placement the sequence starts from
  san: string[];           // one entry per ply
  uci: string[];           // the same moves, for reproduction
  fenAfterPly: string[];   // placement after each ply, for the reveal schedule
  visibility: BoardVisibility;
  history: MoveHistoryVisibility;
  pacing: MovePacing;
  speakMoves: boolean;
  startTurn: PieceColor;
  kind: string;            // which question this is, for progress
}
```

The answer itself lives in `question.expected`, exactly as for every other
mode. Nothing about the presentation can disagree with the answer, because the
presentation carries no answer.

`question.board.fen` is the **start** of the sequence, never the end. The
position the moves produce is the answer to most tracking questions, so it is
never drawn while the question is live — `useBlindfoldPlayback` refuses to draw
the board once every ply has been shown, at any stage, including the most
generous one.

## Sequence generation

`src/core/chess/sequence.ts`. This is the load-bearing module.

A sequence is generated by playing weighted-random legal moves through chess.js
and then **replaying the result through a fresh chess.js instance** to confirm
it. SAN, UCI, the position after every ply, the final FEN, the side to move and
every capture are recorded facts, not the generator's opinion.

### Rules it follows

- **Piece identity, not piece type.** Each piece has an id of
  `${color}-${type}-${origin}`, so "the knight that started on g1" survives a
  promotion (the type changes, the identity does not) and a castle (the rook
  moves with the king).
- **En passant victims are resolved before the move is applied**, because the
  captured pawn is not on the destination square:
  ```ts
  const capturedSquare = chosen.flags.includes('e')
    ? `${chosen.to[0]}${chosen.from[1]}`
    : chosen.to;
  ```
- **Shuffling is discouraged.** Moving a piece straight back where it came from
  is penalised, as is moving the same piece repeatedly. A sequence that is one
  knight hopping about teaches nothing.
- **Capture bias is a preference, not a guarantee.** `requireSequence` returns
  the capture-heaviest sequence it found if it cannot meet the requested
  minimum, rather than failing. A four-ply sequence cannot fit two captures,
  and demanding it used to crash the session.
- **Failure is loud.** If no legal sequence of the requested length can be
  built at all, generation throws. There is no canned fallback position — the
  third pass learned what a silent fallback does.

### Reproducing a sequence

Everything is seeded. To reproduce a question exactly:

```
http://localhost:5173/?mode=blindfold-tracking&variant=mixed&seed=<seed>&debug=1
```

`?debug=1` shows the diagnostics panel, which prints the mode, variant, seed,
the expected answer, and — for blindfold questions — the kind, ply count,
visibility, the SAN of the whole sequence, hints used, and how many pieces are
currently placed. The panel exists only in a development build.

In a test:

```ts
const question = generateTrackingQuestion(context({ plies: 10 }), createRng(seed), 'mixed');
```

Same seed, same context, same question. Asserted by
`blindfold.test.ts > is reproducible from a seed`.

## Question kinds

The mixed tracking variant draws from seven kinds. Each is recorded on the
attempt as `blindfoldKind`, so progress can tell them apart.

| Kind | Asks | Balance rule |
| --- | --- | --- |
| `piece-location` | Where a named piece ended | Only ever about a piece that **survived** |
| `square-contents` | What stands on a square | 60/40 occupied/empty |
| `occupancy` | Is a square occupied | 50/50, so neither answer is a safe guess |
| `side-to-move` | Whose move it is | Only when the ply count is odd — otherwise it is free |
| `was-captured` | Is a named piece still on the board | 50/50 survivors and victims |
| `what-was-captured` | What a named capture took | Only when there are captures |
| `attacks` | Does a piece attack a square, in the final position | 50/50 yes/no |

The balance rules matter: a question type whose answer is usually "yes" trains
guessing.

## Reconstruction

Three variants, all answered with `ExpectedAnswer.kind === 'placement'`.

| Variant | Board starts | `exact` | Asks for |
| --- | --- | --- | --- |
| `partial` | empty | `false` | A named subset: both knights, every queen and rook, all White, both kings… |
| `full` | empty | `true` | Every surviving piece |
| `correction` | the position **with 1–3 deliberate errors** | `true` | The true position |

### The interaction

Tap a piece in the palette, then tap a square. The armed piece **stays armed**,
so a run of pawns is one palette tap and eight squares.

- A correct placement stays on the board.
- A wrong one flashes red and is discarded.
- The question completes itself the moment the position is right. There is no
  Submit button anywhere.

The palette always offers **all twelve pieces with no counts**. A palette
showing only what is still needed would hand over the entire material balance,
which is exactly what the drill is asking the user to have held in their head.

### Grading, and where completion is decided

`state.placed` is the live board. It is seeded from `question.board.fen`, so
the correction variant starts with the damaged position already on it and the
other two start empty — no second mechanism.

Completion is decided by `gradeQuestion`, not by counting pieces, so "is this
finished" and "was this right" cannot drift apart. That matters on the
correction variant, where a leftover piece in the wrong place is a failure even
though nothing is missing.

Clearing a square is a real answer: removing an intruder can complete the
question. Clearing a piece that belongs where it stands is a mistake and is
rejected like any other, at no cost beyond the flash.

## Hints

One hint: **show the moves again**. It gives back the move list the user was
shown and asked to remember — help with recall, not with the chess. It is
offered only when the move list was hidden in the first place, and only when
hints are enabled.

Hint use is recorded on the attempt (`hintsUsed`) and reported separately as
hint-free accuracy. **A hinted answer is never counted as a mistake.** Nothing
in the wording scolds the user for taking one.

## Difficulty presets

Four presets in `BLINDFOLD_PRESETS`. Choosing one **writes into the ordinary
settings**, which stay editable — a starting point, not a separate system.

| Preset | Plies | Board | Move list | Captures |
| --- | --- | --- | --- | --- |
| Beginner | 4 | after each full move | visible | ordinary |
| Intermediate | 10 | start only | last move only | more |
| Advanced | 18 | never | hidden | more |
| Expert | 24 | never | hidden | heavy |

**No preset claims a chess rating**, and a test asserts the descriptions
contain no rating-shaped number.

## Progress

`src/core/progress/blindfold.ts`, deliberately separate from square mastery.

**Blindfold attempts are excluded from `computeMastery` outright.** Getting
"where is the knight that started on g1" wrong means the user lost track of a
piece, not that they do not know where e5 is. Crediting it to e5 would make
squares they know perfectly well look weak, and adaptive practice would then
drill the wrong thing.

What is measured instead: accuracy, hint-free accuracy, accuracy by sequence
length, by question kind, by board visibility and by orientation; distinct
sessions and days; accuracy over the recent window; and `provenPlies` — the
longest sequence answered correctly **without hints** at least five times at
70% accuracy. Deliberately not "the longest they ever got right once".

The Progress card shows three numbers, a recommendation, accuracy by length,
and the three hardest question kinds. Not a wall of numbers.

Recommendations are a fixed, dull ladder: no evidence → not enough evidence →
not holding this length → holding it with the board still on → holding it
without. Every one names the numbers it acted on, because a suggestion the user
cannot check is indistinguishable from a guess.

## Storage

Four optional fields were added to `Attempt`:

| Field | Meaning |
| --- | --- |
| `hintsUsed` | Hints taken before this answer |
| `plies` | How long the sequence actually was |
| `boardVisibility` | How much board the user actually got |
| `blindfoldKind` | Which question this was |

All optional, so **the schema version is unchanged and no migration exists**.
A backup written by 1.3.0 imports untouched and reads as "not recorded" rather
than as a default that would be a lie. `blindfoldBackup.test.ts` holds that to
account.

`plies` and `boardVisibility` are denormalised onto the attempt rather than
read from the session's settings, because the progressive ladder can move the
stage mid-session: the settings say what the user *chose*, the attempt says
what they were *given*.

## Testing

| Layer | File | Approach |
| --- | --- | --- |
| Sequence | `core/chess/sequence.test.ts` | Replay every generated sequence through a fresh chess.js |
| Questions | `core/training/generators/blindfold.test.ts` | Re-derive every answer from an independent replay, never from the generator |
| Interaction | `core/session/blindfold.test.ts` | Drive the real generator through the real engine |
| Variety | `core/session/blindfoldRetry.test.ts` | Distributions over a 120-question run |
| Progress | `core/progress/blindfold.test.ts` | Including that mastery is untouched |
| Persistence | `core/backup/blindfoldBackup.test.ts` | Round trips, and 1.3.0 backups |
| UI | `ui/Blindfold.integration.test.tsx` | The real screen |
| Layout | `scripts/browser-tests.mjs` | Real Chromium, four viewports |
| End to end | `scripts/blindfold-walkthrough.mjs` | Every flow actually completed in a browser |

The rule worth keeping: **never assert against the generator's own
bookkeeping.** A generator that wrote down its own answer key would pass such a
test and still be wrong. Replay the moves and ask chess.js.

## Adding a question type

1. Add the kind to `TrackingKind` and to `kindsForVariant`, with the condition
   under which it is askable (`what-was-captured` needs a capture to exist).
2. Add a `case` in `generateTrackingQuestion` producing a `Question` whose
   `expected` is derived from the **sequence**, never invented.
3. Give it a `kind` string and a label in `KIND_LABELS`.
4. Balance the answer. If one answer is more common than the other, say why or
   fix it.
5. Add a test that re-derives the answer from a replay, plus a balance test if
   the answer is binary.
6. Check `blindfold.test.ts > produces every kind of question in the mix` still
   passes — it asserts the mix reaches every kind.

Before adding a whole new *mode*, check it is not a variant of an existing one.
The mode-count guards will refuse a fourth card in this category, and that is
the guard working, not an obstacle to route around.

## Known limitations

- **Sequences are generated, not curated.** They are legal and varied but not
  instructive — no opening theory, no thematic middlegames. A curated source
  would be a genuine improvement.
- **Never run on Android hardware.** Every layout and behaviour claim comes
  from Chromium at phone viewports.
- **Speech is untested here.** `speakMoves` calls the same `speak()` the rest
  of the app uses, but no blindfold-specific speech test exists.
- **The progressive ladder is per-session.** It reads the current streak and
  recent accuracy, so it starts from the chosen stage every session rather than
  remembering where the user got to.
